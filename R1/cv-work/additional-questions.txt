## Azure Compute Choices
How do App Service Functions and Container Apps differ|I would compare the execution model first. App Service suits hosted web applications; Functions suits event-triggered code; Container Apps hosts containerized services and workers with managed operations. I would check runtime support, networking, scaling, execution duration, and operational requirements before selecting a service. A small representative workload is more useful than choosing from a feature list.
How do you handle cold starts|I would measure which part of initialization causes the delay, such as package loading, identity setup, or connections. I would reduce unnecessary startup work and consider warm capacity where the hosting plan supports it. The decision depends on latency requirements and idle cost. I would test after idle periods and deployments rather than assume steady-state measurements cover startup behavior.
How would you run a long background job|I would persist the job and place a durable dispatch request on a queue. Workers would checkpoint progress and use bounded retries, cancellation, and time limits. The web request would return a job identifier rather than remain open for minutes. I would verify whether work can be repeated safely and how a failed worker transfers ownership without duplicating external actions.
How would you select an Azure region|I would consider where users and data are located, permitted processing locations, service and model availability, recovery requirements, quota, and cost. I would measure latency to dependencies and verify the selected deployment types. I would also assess paired recovery resources and data movement. Geography alone does not guarantee every required service or model is available with sufficient capacity.
## Azure Networking
What is the role of a virtual network and subnets|A virtual network provides an address space and connectivity boundary for Azure resources. Subnets organize that space and support different workload and policy requirements. I would plan addresses to avoid overlap with connected networks, separate workloads where useful, and document routes and dependencies. Network segmentation complements identity controls; it does not replace authorization at the application or resource.
How do NSGs and a firewall differ|I would use network security groups for applicable network traffic rules around subnets or interfaces, and a firewall where centralized inspection and broader traffic policy are needed. I would evaluate direction, address, port, routing, and required application controls. Troubleshooting starts with the actual path: a correct rule is ineffective if traffic bypasses the intended inspection point.
How do you diagnose a private endpoint connection failure|I would check name resolution from the application environment, the resolved address, routing, security rules, endpoint approval, and service access configuration. I would separate connectivity from authentication and authorization errors. I would compare a working and failing client and examine recent changes. Making a service publicly reachable is not my default remedy for incorrect private DNS or routing.
What is the difference between Front Door and API Management|I would use Front Door for appropriate edge delivery and routing requirements, while API Management governs and exposes APIs through policies and contracts. They can be complementary. I would determine where authentication, throttling, caching, and routing belong and avoid duplicate or inconsistent policies. The exact topology follows the application, security requirements, and chosen service features.
## Identity and Access Operations
How would you apply least privilege|I would list the actions each identity needs, grant the narrowest useful permissions at an appropriate scope, and test denied operations. Deployment, runtime, and human support identities should have distinct responsibilities. I would review permissions periodically and after role changes. Least privilege must include data access and tool actions, not only the cloud management plane.
How do system assigned and user assigned managed identities differ|A system-assigned identity is associated with the lifecycle of its resource. A user-assigned identity is a separately managed resource that can be assigned where supported. I would choose based on lifecycle and governance needs, then restrict sharing to avoid excessive privilege. Neither choice eliminates the need to configure permissions or verify which identity the workload actually uses.
How would you provide emergency production access|I would agree on a controlled emergency process with restricted eligibility, time-limited access where supported, and an audit trail. The operator should know the incident scope and recovery steps. Afterward, I would remove temporary access and reconcile emergency changes into code. A standing broad administrator role for every engineer makes access easy but weakens accountability and containment.
What would you do after a credential leak|I would identify the affected identity and scope, revoke or rotate the credential, inspect usage, and contain unauthorized access. I would check copies in logs, artifacts, and deployment configuration, then deploy the replacement safely. I would verify dependent workloads and preserve evidence. Removing the secret from the latest commit alone does not invalidate it or remove previous exposure.
## Storage and Document Handling
How would you handle large document uploads|I would avoid loading the whole upload into application memory. A controlled direct-to-storage flow can reduce API pressure, with scoped authorization, size limits, expiry, and validation. The service would persist metadata and process uploads asynchronously. I would handle incomplete uploads and verify file content before downstream parsing. User-supplied names should not determine unrestricted storage paths.
How would you protect uploaded documents|I would authorize tenant access, use restricted storage permissions, validate file type and size, and scan where required before parsing. I would define retention and deletion behavior, log access without exposing contents, and limit parser resources. Sensitive data needs protection in temporary files and derived indexes as well as the original object. The document processing worker should have narrow privileges.
How do you choose a retention policy|I would ask which data is needed for business use, audit, support, and recovery, then define retention by category. Documents, derived embeddings, agent state, backups, and telemetry can require different rules. I would document deletion behavior and validate it across copies. Indefinite retention increases cost and exposure; immediate deletion may conflict with agreed recovery or audit needs.
How would you recover an accidentally deleted object|I would first confirm the object, deletion time, and available protection settings. Recovery might use enabled soft delete, versioning, or a backup, depending on the service configuration. I would verify the restored content and permissions and assess downstream indexes. I would not promise recovery merely because the resource is hosted in Azure; recoverability depends on prior configuration and tested procedures.
## Database Selection and Data Modeling
How would you choose SQL or a document database|I would examine access patterns, relationships, transaction needs, consistency, query flexibility, and scale. A relational database is a strong starting point for structured run state and transactional records. A document store can suit appropriate document-oriented access patterns. I would model a representative query and failure case before choosing, and include indexing, operations, and cost in the comparison.
How would you model agent run state|I would store the run identifier, tenant, status, timestamps, configuration version, progress, cancellation state, and result references. Steps would record attempts and externally visible effects where necessary. I would define permitted state transitions and enforce them with concurrency controls. Large documents and outputs can be referenced rather than duplicated in every run record. Sensitive fields need explicit retention and access controls.
How do you choose a partition key|I would examine how queries distribute load and how data grows. A key should support common access patterns while avoiding a hot partition. Tenant ID may help isolation but can concentrate a very large tenant's traffic. I would consider composite strategies where supported and understand cross-partition query costs. The decision should use expected distributions, not only average tenant size.
What is eventual consistency and when is it acceptable|Eventual consistency allows copies or projections to converge over time instead of requiring every read to observe the latest change immediately. I would use it when the user workflow tolerates delay, such as a derived dashboard. I would make pending states visible and define maximum acceptable lag. Authorization and critical state transitions may require stronger guarantees than an analytics projection.
## Database Transactions and Concurrency
What is a lost update and how do you prevent it|A lost update occurs when concurrent writers overwrite each other's changes without detecting the conflict. I would use an appropriate transaction, row version or expected version check, or a suitable locking strategy. On conflict, I would retry only if the operation remains safe. For an agent run, two workers must not independently advance the same step and duplicate a side effect.
How do isolation levels affect correctness|Isolation controls what concurrent transactions can observe. Weaker isolation can allow anomalies; stronger isolation can require waiting or transaction retries. I would identify the invariant being protected and choose the database behavior that enforces it, then test competing transactions. I would not assume an isolation level has identical implementation details across database engines. [S12]
How would you investigate a database deadlock|I would capture the database's deadlock evidence and identify the transactions, resources, and order of access. I would reduce transaction duration, use consistent access order, and improve indexes where that reduces locking. A bounded retry may handle a victim transaction if repeating it is safe. Increasing timeout does not remove the circular dependency that caused the deadlock.
Why should a transaction not remain open during an LLM call|A slow or unpredictable external call can keep database locks and connections occupied, increasing contention and failure impact. I would persist a pending workflow state, perform the external call outside the transaction, then record its outcome with concurrency checks. Where side effects cross systems, I would use durable state and idempotency rather than pretend a database transaction covers the remote model or tool.
## Database Performance
How would you diagnose a slow query|I would inspect the query plan, filters, joins, row counts, indexes, wait conditions, and recent data growth. I would measure representative parameters and distinguish database execution from connection-pool wait or network time. A suitable index or smaller result can help, but I would evaluate write overhead and storage. I would validate improvement using the same workload and tail latency.
What is the N plus one query problem|It occurs when one initial query triggers an additional query for each returned item. I would identify it through query counts and traces, then use an appropriate join, batch fetch, projection, or loading strategy. I would avoid fetching excessive related data just to reduce query count. The aim is less total work and predictable performance for the actual response shape.
How would you handle connection pool exhaustion|I would inspect active and waiting connections, long transactions, slow queries, leaked connections, and aggregate demand from all application replicas. I would ensure connections are released and impose bounded concurrency. Increasing the pool may shift overload to the database. I would measure whether the real limit is database capacity or poor application behavior before changing pool sizes.
When is read replication helpful|It can offload eligible reads and support recovery designs, but replicas can lag. I would direct only suitable queries to replicas and preserve required read-after-write behavior. I would monitor lag and define fallback behavior when replicas are unhealthy. Replication does not fix inefficient queries automatically and does not replace a tested backup against logical corruption or deletion.
## Caching and Redis
Explain cache aside|The application checks the cache, loads missing data from the backing store, and populates the cache. I would set a deliberate expiry and handle updates so stale data stays within the allowed window. This improves suitable repeated reads but introduces consistency and invalidation concerns. Authorization-sensitive data must remain correctly scoped even when a cached value is reused. [S18]
What is a cache stampede|Many requests can miss or expire on the same key and hit the backing store at once. I would consider coalescing refreshes, staggered expiry, or controlled serving of permitted stale data. I would also limit fallback concurrency. The solution depends on freshness requirements; a financial or permission decision may not tolerate the same stale-data policy as a public reference list.
What belongs in a cache key for tenant data|The key must include the tenant and all relevant dimensions that change the authorized result, such as resource, version, locale, or access scope. I would avoid placing raw secrets or personal data in keys. I would review permission changes and invalidation. A cache hit should not bypass an authorization decision simply because the data was previously returned to another user.
What happens if Redis becomes unavailable|I would define which functions can safely fall back and which depend on Redis for correctness. Read caching may bypass to the database with strict load limits. A coordination or rate-limit function needs an explicit failure policy. I would monitor fallback impact and avoid turning a cache outage into a database outage. The policy should follow the consequences of allowing or rejecting work.
## Messaging Service Selection
How do queues and publish subscribe differ|A work queue commonly distributes tasks among competing consumers. Publish-subscribe sends an event to interested subscribers, each with its own processing responsibility. I would choose based on whether one worker should perform a job or multiple services should react independently. Delivery guarantees, ordering, retention, and retry behavior depend on the actual broker and configuration.
When would you consider Service Bus or Event Hubs|I would consider Service Bus for business messages and workflows that need broker features such as queues or subscriptions. Event Hubs suits high-volume event ingestion and stream processing patterns. I would verify ordering, retention, delivery, and consumer behavior for the chosen design. My decision would follow message semantics and processing requirements rather than throughput claims alone.
What is a consumer group|In stream-processing systems, a consumer group gives a logical consumer its own progress through the stream. Multiple groups can process the same events independently. Within a group, partition assignment affects parallelism. I would plan checkpointing and recovery and verify broker-specific behavior. Adding consumers beyond available partitions may not increase processing parallelism for that stream.
How would you version an event schema|I would prefer compatible additive changes and document the contract, field meanings, and defaults. Consumers should handle supported versions deliberately and ignore harmless extra fields where appropriate. Breaking changes need a transition plan and testing with old consumers. I would retain enough metadata for replay and distinguish the event's business time from its publication or processing time.
## Reliable Message Processing
What belongs in a dead letter queue workflow|I would capture the reason for failure, alert the owner, and provide controlled inspection and reprocessing. Service Bus dead-letter messages require explicit handling; the queue is not a substitute for a recovery process. Before replay, I would correct the cause and assess idempotency. Sensitive payloads and diagnostic details need the same access protections as other production data. [S14]
How do you deal with duplicate messages|I would assume duplicates are possible and make processing idempotent. The consumer can use a durable event or operation identifier with a uniqueness constraint around its state change. I would define how long deduplication records remain useful and what happens on concurrent delivery. An in-memory set on one worker is insufficient when workers restart or messages reach another replica.
How would you preserve ordering|I would identify the smallest scope that requires order, such as one booking or one account, then choose an appropriate partitioning or session mechanism. I would record sequence or version information when needed and handle gaps deliberately. Global ordering can restrict throughput unnecessarily. I would also explain how retries or parallel consumers can affect the order observed by the application.
How do you safely replay historical events|I would select the scope and event versions, verify consumer compatibility, and isolate replay from live work where necessary. I would prevent duplicate external actions and control throughput. I would monitor progress and compare the resulting state with expected invariants. Replay can rebuild projections, but repeating irreversible side effects requires an explicit policy rather than ordinary consumer execution.
## Microservice Resilience
What is a circuit breaker|A circuit breaker temporarily stops calls to a dependency after a configured failure pattern, then allows limited recovery checks. It differs from retrying each failed request. I would select thresholds and fallback behavior based on the dependency and user impact, and measure trips and recovery. It prevents repeated pressure on a failing service but cannot create a correct substitute result. [S15]
What is the bulkhead pattern|It isolates resource pools so failure or saturation in one workload does not consume all shared capacity. I might separate worker pools, concurrency budgets, or connection limits for critical and optional tasks. I would ensure the boundaries align with failure risks and monitor rejected work. Too many isolated pools can waste capacity, so the design needs a measured balance.
How do you propagate timeouts|I would establish an overall deadline and allocate smaller per-call timeouts so downstream work leaves time for cleanup and response. Cancellation should flow where supported, and retries must fit inside the remaining deadline. Independent long timeouts at every layer can make total latency unpredictable. I would monitor timeout location to distinguish overload from genuine dependency failure.
When would you use a saga|A saga coordinates a business workflow across services through local transactions and compensating actions. I would use it when one database transaction cannot cover the workflow. I would record progress and retries durably and define failure handling at every step. A compensation is a business operation, not always a perfect reversal; sending an email or exposing a report may be irreversible.
## API Contracts and Compatibility
What makes an API change backward compatible|Existing clients should continue to operate with the agreed meaning of fields, status codes, and behavior. Adding an optional field can be compatible; changing a type or making an optional field required can break clients. I would use contract tests and staged adoption. Compatibility includes timing and errors, not only whether a JSON document still parses.
How would you design pagination|I would choose a stable ordering and bound page size. Cursor pagination often suits changing datasets and large offsets, while offset pagination can be adequate for simpler cases. I would define filter and cursor validity, avoid exposing internal secrets, and test inserts or deletes between requests. Authorization must apply to each page rather than only the initial request.
How would you design API error responses|I would return consistent machine-readable codes, useful safe messages, and a correlation identifier. Validation errors should identify the relevant input without disclosing sensitive data. HTTP status should reflect the failure class, and clients should know which errors are retryable. I would retain detailed internal diagnostics in controlled telemetry rather than reveal stack traces or credentials in the response.
When would you choose REST GraphQL or gRPC|I would use REST for straightforward resource-oriented integration, GraphQL when clients need flexible composition with controlled query costs, and gRPC for suitable typed service-to-service calls. I would consider client support, observability, caching, security, and operational complexity. A mixed architecture can be reasonable, but each interface needs a clear purpose and ownership.
## API Security and Traffic Controls
What should you validate in a JWT|I would validate the signature against trusted keys, expected issuer and audience, lifetime, and required claims. Then I would separately authorize the requested action and resource. I would handle key rotation through the identity provider's supported mechanism. Decoding the payload alone does not authenticate it, and accepting any valid token without checking audience can allow a token intended for another service.
How do you choose a rate limiting policy|I would identify what is scarce or expensive and limit by an appropriate authenticated identity, tenant, or operation. Request count alone may not reflect model token or compute cost. I would provide clear overload responses and retry guidance, protect critical traffic, and monitor fairness. Distributed enforcement needs a shared or otherwise coordinated view of allowances where the policy requires it.
Does CORS secure an API|CORS controls which browser origins can read permitted cross-origin responses; it is not an authentication or authorization mechanism. I would still validate identity, permissions, and request semantics. Nonbrowser clients are not constrained in the same way. If cookies authenticate requests, I would separately consider CSRF protections. A permissive CORS setting should not become a substitute for a security design.
How would you protect against SSRF through an agent tool|I would avoid arbitrary user-controlled destinations where possible and restrict schemes, hosts, ports, and reachable networks. I would validate resolved addresses and redirects and enforce outbound network controls. The tool would have limited credentials and time or size limits. A string check on the original URL alone is insufficient because resolution and redirects can change where the request goes.
## Python Fundamentals
What are generators useful for|Generators produce values incrementally, which can reduce memory use for large or streamed datasets. I would use them when downstream work can also process incrementally. A later conversion to a list removes much of the memory advantage. I would consider cleanup, exceptions, and whether iteration can be repeated, especially when a generator reads a file or network stream.
Why are mutable default arguments dangerous|A mutable default object can be shared across calls, creating surprising retained state. I would normally default to None and create a fresh list or dictionary inside the function when needed. I would also inspect shared class attributes and caches for similar unintended state. A small repeated-call test helps reveal this issue before it becomes a request-isolation bug.
When would you use threads or processes in Python|I would use an approach that matches the work and interpreter environment. Threads can help with blocking I/O; processes can provide parallel execution and isolation for CPU-heavy tasks. Async clients suit cooperative I/O. I would account for serialization, process startup, library behavior, and deployment limits. I would benchmark the actual workload rather than assume one concurrency model is always faster.
How would you manage Python resources safely|I would use context managers and try/finally where needed to close files, transactions, and connections even on failure. For asynchronous resources, I would use their async lifecycle mechanisms. I would keep ownership explicit and avoid opening a client for every tiny operation unnecessarily. Cancellation and exceptions should not leave a connection or temporary file permanently occupied.
## FastAPI and Python Service Lifecycle
How do you decide between def and async def in FastAPI|I would use async def when calling suitable awaitable clients, and understand how the framework handles ordinary synchronous path functions. A blocking call directly inside an async endpoint can block its event loop. I would inspect the libraries used and move unsuitable work to an appropriate execution context. Merely changing the function declaration does not make synchronous I/O nonblocking. [S9]
What would you initialize at service startup|I would initialize reusable clients, validate required configuration, and establish resources whose lifecycle matches the application. Startup should fail clearly for unrecoverable configuration errors. I would avoid performing lengthy migrations independently in every replica. Shutdown should release clients and finish or safely stop active work. Resource initialization belongs in an explicit lifecycle path with tests for startup failure.
Are in process background tasks durable|Generally, they depend on the application process staying alive and may be unsuitable for work that must survive restarts. I would use a durable queue and worker for critical or long-running jobs. I would define accepted-work semantics, persistence, retries, and status tracking. Lightweight post-response work can be appropriate when its loss is tolerable and the framework behavior is understood.
How would you validate an API request in Python|I would use an explicit request schema, constrain lengths and sizes, and validate business rules after structural validation. I would reject unknown or conflicting input according to the contract and avoid trusting client-supplied authorization fields. I would keep response schemas separate where sensitive internal fields must be excluded. Type annotations help communicate intent but do not enforce every business invariant.
## Node js and TypeScript
Why can a Node service be slow with few active requests|A callback can monopolize the event loop through heavy computation, large synchronous operations, or expensive input processing. I would measure event-loop delay and profile the workload, then partition work or move suitable work to workers. I would also inspect the worker pool and downstream waits. Low request volume does not mean each request performs little work. [S10]
What does TypeScript fail to validate at runtime|Static types do not validate arbitrary JSON, environment variables, database records, or external messages at runtime. I would use explicit boundary validation and then work with trusted types internally. An assertion or cast does not transform the data into the declared shape. I would test malformed payloads and avoid allowing unchecked external input to reach privileged tool calls.
Why can Promise all cause overload|It can start a large number of operations together without limiting concurrency. I would use bounded batches or a worker pool when the dependency has capacity or quota limits. I would define cancellation and partial-failure behavior and preserve relevant results. Parallelism reduces time only while the bottleneck has spare capacity; uncontrolled fan-out can increase latency and error rates.
How would you handle asynchronous errors in Node|I would await or deliberately manage each promise, map expected failures to consistent responses, and ensure background tasks have explicit error handling. Unexpected process-level failures need a defined shutdown and restart strategy. I would include context in logs without leaking secrets. Catching every error and returning success hides failed work and makes diagnosis more difficult.
## ASP NET Core and C Sharp
How do dependency injection lifetimes affect a service|Transient, scoped, and singleton services have different reuse and ownership behavior. I would choose based on state, thread safety, and resource lifecycle. A singleton should not capture a request-scoped dependency improperly. For background work, I would create an appropriate scope rather than reuse a completed request's resources. A lifetime mistake can cause leaked state, concurrency faults, or disposed-object errors.
Why avoid blocking on async work in ASP NET Core|Blocking waits consume request-processing capacity and can contribute to thread-pool starvation under load. I would keep I/O paths asynchronous end to end where supported and propagate cancellation. I would measure throughput and tail latency rather than add threads as the first fix. CPU-heavy work needs a separate capacity decision; async does not make the computation cheaper. [S11]
How would you use HttpClient safely|I would use a supported reuse and configuration pattern, such as a suitable factory or managed client lifetime, rather than casually create and dispose a new client for every request. I would configure deadlines, connection behavior, and dependency policies. I would avoid layering retries without understanding their combined effect, and verify behavior during DNS changes and dependency outages.
How do you decide between EF Core and direct SQL|I would consider maintainability, query complexity, performance, and transaction requirements. EF Core can be productive for common data access; direct SQL can be suitable for carefully optimized or specialized queries. I would inspect generated SQL, avoid excessive loading, and use parameters. The decision should follow measured requirements rather than a claim that an ORM is inherently too slow.
## Frontend and Backend Collaboration
How would you stream agent progress to a frontend|I would define events and terminal states, choose a suitable transport such as SSE or WebSockets, and preserve authorization and reconnect behavior. The UI should distinguish partial output from a completed result. I would decide whether events can be replayed and how the client detects gaps. Streaming improves perceived progress but does not replace durable run state.
What should the UI show for a long running task|I would show the run state, meaningful progress where available, cancellation options, and a stable link or identifier. After refresh, the UI should restore status from the server. Failure should provide a useful next action rather than silently restart the task. The design must not imply success merely because the server accepted the request or produced partial output.
How would you handle frontend API contract changes|I would agree on the contract with frontend engineers, provide realistic examples, and test both error and success flows. New fields or endpoints would be adopted in stages while older clients remain supported for the agreed window. I would use contract validation where useful. Shared TypeScript types are helpful but do not guarantee compatibility with a separately deployed backend.
How do you keep a frontend from exposing credentials|I would keep privileged service credentials on controlled backend services and use the user's appropriate authentication flow for browser access. Build variables shipped to a browser should be considered public. I would review logs, source maps, and client telemetry for accidental exposure. If direct storage access is needed, I would issue narrowly scoped short-lived access through an authorized backend.
## CI Pipeline Engineering
What should be cached in a build pipeline|I would cache reproducible dependencies or intermediate work with keys that reflect relevant lockfiles, toolchains, and build inputs. I would avoid caching credentials or mixing untrusted and privileged artifacts. A cache miss should remain correct. I would measure whether caching saves meaningful time and ensure stale entries cannot silently change the released artifact or bypass a required verification step.
How would you handle a flaky test|I would capture conditions and determine whether the flakiness exposes a real race, uncontrolled dependency, or test problem. I would fix isolation, synchronization, or the underlying defect. Temporary quarantine needs an owner and deadline. Blind retries can hide genuine failures. I would track flake rate and avoid weakening important release checks solely to make the dashboard green.
How do you secure pull request pipelines|I would treat code from untrusted changes as untrusted execution. I would restrict secrets, token permissions, privileged runners, and artifact promotion paths. Production deployment should require the intended reviewed context. I would pin or review external actions as appropriate and examine how scripts use input. A successful test run should not automatically grant arbitrary production access.
How do you prove what was deployed|I would record the source revision, immutable artifact digest, build run, configuration version, and deployment history. Release metadata should appear in operational telemetry and a deployment record. I would verify that promotion uses the same artifact rather than a new build. This makes incident comparison and recovery more reliable than relying on a mutable tag called latest.
## Release Strategies
How do blue green and canary deployments differ|Blue-green maintains separate versions and changes traffic between them; canary exposes a limited portion of traffic before expanding. I would choose based on routing support, cost, state, and the signals available to judge health. Both require a plan for data compatibility and recovery. A second environment alone does not guarantee that switching back will reverse every side effect.
What metrics should stop a rollout|I would use signals tied to user outcomes, such as elevated error rate, latency, failed completions, or unexpected tool behavior. I would compare the new version with a relevant baseline and require enough observation to make the decision useful. Thresholds and sample sizes depend on traffic and risk. I would also watch dependency pressure and cost anomalies rather than only container readiness.
How would you remove an obsolete database field|I would first deploy code that tolerates both old and new schema and migrate data if necessary. After verifying consumers no longer depend on the old field, I would remove it in a later controlled change. I would include background jobs and reports in dependency checks. Deleting the field in the same release as the first code change makes rollback harder.
When are feature flags useful|They can separate deployment from exposure and provide a targeted way to disable a feature. I would define safe defaults, ownership, authorization for changes, and removal dates. Flags must be tested in meaningful combinations and observed in telemetry. A flag cannot reverse irreversible data changes automatically, and accumulating abandoned flags makes behavior harder to reason about.
## Terraform Practice
Why protect Terraform state|State maps configuration to managed resources and can include sensitive values. I would store it in an appropriately protected remote backend, restrict access, enable suitable recovery protections, and use locking where supported. I would separate unrelated failure domains deliberately. Marking a value sensitive can reduce display exposure, but it does not mean no sensitive value exists in the state.
How would you organize Terraform modules|I would create modules around coherent infrastructure responsibilities with clear inputs and outputs, keeping environment configuration separate. I would avoid abstractions that hide important lifecycle or security behavior. Module and provider changes would be versioned and reviewed. I would start with repeatable patterns actually needed by the project rather than make every single resource a separate generic module.
What would you review in a Terraform plan|I would inspect creates, replacements, and deletions; permission and network changes; state or address changes; and impacts on data-bearing resources. I would confirm the environment and input values and ensure the plan corresponds to the reviewed code. An apparently small configuration edit can trigger a disruptive replacement, so I would assess operational consequences before applying it.
How would you bring an existing resource under IaC|I would inventory its configuration and dependencies, write the matching configuration, and use the tool's appropriate import mechanism. I would review the resulting plan until it reflects intended changes rather than accidental replacement. I would back up relevant state and document ownership. Importing an identifier does not automatically produce a correct long-term configuration or settle drift decisions.
## Bicep and Azure Governance
What does Bicep what if tell you|It previews expected resource changes before deployment and is useful for review, but it has limitations. I would inspect changes alongside dependency behavior and operational impact and verify the target scope and parameters. I would not treat a preview as proof that the application remains healthy or that no data will be affected. A post-deployment validation remains necessary. [S2]
What is Azure Policy for|I would use Azure Policy for applicable resource governance, such as evaluating or enforcing agreed configuration requirements. I would test policies and their effects before broad enforcement and assign exception owners. Policy complements access control and application security. A compliant resource configuration does not guarantee the workload's business logic or tenant authorization is correct.
How would you standardize resource tags|I would define a small required set, such as owner, environment, application, and cost allocation category, then apply it through infrastructure modules and suitable governance. I would validate coverage and keep ownership current. Tag-based reporting helps only if tags reflect reality. I would also understand which costs cannot be cleanly allocated through resource tags alone.
How do locks differ from permissions|Resource locks can add protection against certain management actions, while permissions determine which actions an identity can perform. I would use each deliberately and verify the affected operation scope. Locks should not be treated as a backup or a comprehensive defense against data changes. Operational procedures must account for them so legitimate recovery does not stall unexpectedly.
## Docker Operations
Why use multi stage builds|They separate build tooling from the final runtime image, helping reduce unnecessary contents. I would copy only required output and verify runtime dependencies. Smaller images can improve transfer and reduce exposure, but size is not the sole security measure. I would scan, patch, and configure the final image and validate that diagnostic and startup requirements are still met.
How would you design graceful shutdown|The process would stop accepting new work, signal active tasks, and finish or checkpoint them within an agreed grace period. Workers should release or settle messages appropriately and avoid claiming success for incomplete work. I would test termination during requests and jobs. A graceful path must fit the platform's termination behavior rather than assume unlimited time before the process is killed.
Why can a container work locally but fail in production|I would compare architecture, environment configuration, filesystem permissions, identity, network access, resource limits, and entrypoint behavior. Local development may provide files or credentials that are absent in the image. I would reproduce with the same artifact and relevant runtime restrictions. Rebuilding a different image locally can conceal the exact production issue instead of explaining it.
How do you reduce container supply chain risk|I would use trusted sources, track dependencies, scan artifacts, record provenance, and deploy immutable references. I would keep build credentials out of images and review third-party build steps. Image signing helps establish origin when verification is enforced. It does not prove that the signed code is vulnerability-free or safe for every runtime permission.
## Kubernetes Networking and Configuration
How do a Service and an Ingress differ|A Service provides a stable way to reach selected workloads inside the cluster or through supported exposure types. Ingress describes applicable HTTP routing handled by a controller. I would inspect selectors, endpoints, ports, routing rules, and TLS when diagnosing connectivity. The controller and underlying networking matter; defining an Ingress object alone does not provide a working traffic path.
How would you troubleshoot service discovery|I would test resolution and connectivity from the affected workload, inspect service names, namespaces, endpoints, and network policy, and compare with healthy clients. I would distinguish DNS failure from a service with no ready backends. I would also inspect recent deployment and cluster changes. Testing only from my laptop does not validate the workload's in-cluster path.
How do ConfigMaps and Secrets differ operationally|They hold different kinds of configuration, but storing a value in a Kubernetes Secret is not by itself a complete security design. I would restrict access, protect storage, avoid exposure in logs, and manage rotation. I would check how applications observe changes and whether restart is required. External secret systems may be appropriate when lifecycle and governance require them.
What should a network policy achieve|I would use supported network policy enforcement to limit communication to required paths and reduce lateral movement. I would begin with a clear dependency map and test DNS, telemetry, identity, and application traffic before rollout. Policies need a functioning enforcement implementation. A policy file that is accepted by the API is not sufficient evidence that the expected traffic is blocked.
## Kubernetes Capacity and Scheduling
What are resource requests and limits|Requests inform scheduling and resource allocation decisions; limits constrain resource use according to the resource type and runtime behavior. I would set them from measured workload needs and monitor throttling or memory termination. Overstated requests waste capacity; understated requests can harm placement and performance. I would account for startup peaks and workload variability rather than choose the same values for every service.
Why might pods remain Pending|I would inspect scheduler events for insufficient resources, affinity constraints, taints, volume issues, or other placement requirements. I would check whether autoscaling can add the needed node type and whether quotas or limits prevent it. Increasing replicas does not resolve unsatisfiable scheduling constraints. I would identify the missing requirement and apply the smallest appropriate correction.
What are taints tolerations and affinity used for|They influence placement by discouraging or allowing scheduling on certain nodes and expressing placement preferences or requirements. I would use them to separate workloads or meet operational needs without creating impossible constraints. I would check their interaction with available capacity and autoscaling. A toleration permits placement on a tainted node; it does not guarantee that the pod will run there.
How would you protect one tenant from another noisy workload|I would define concurrency and resource boundaries, prioritize critical work, and consider separate queues or worker pools. In Kubernetes, namespace and scheduling controls can contribute, but application-level fairness is still needed. I would monitor tail latency and rejected work by tenant. Maximum replicas alone cannot prevent a single tenant from consuming every downstream model or database allowance.
## Kubernetes Lifecycle and GitOps
What is a PodDisruptionBudget for|It constrains certain voluntary disruptions to preserve a desired level of availability. I would align it with replica count, placement, and maintenance procedures. It does not prevent all failures or guarantee application health. A configuration that permits no useful maintenance can stall node updates, so I would test both service continuity and the ability to perform planned operations.
How would you upgrade a production cluster|I would verify supported version paths, workload API compatibility, add-ons, capacity, and maintenance constraints. I would test in a representative environment, plan node upgrades and disruptions, and monitor service behavior during rollout. Recovery options depend on the platform and change type, so I would not promise a simple in-place downgrade. Application recovery and infrastructure recovery need separate plans.
What does GitOps reconciliation do|A controller compares observed resources with declared desired state and attempts to reconcile differences according to its configuration. I would review permissions, sync behavior, drift handling, and rollout health. It improves repeatability and history but can also undo manual emergency changes. I would coordinate emergency fixes with the declared state and record why any reconciliation suspension was needed.
What happens when a rollout never becomes healthy|I would inspect the Deployment conditions, new pod failures, readiness, events, and available old replicas. I would stop promotion and take the appropriate recovery action. Kubernetes reports rollout problems, but a Deployment should not be assumed to automatically choose and execute the desired rollback policy. The delivery system must define how failed health checks lead to recovery. [S17]
## Telemetry Design
How do metrics logs and traces complement each other|Metrics summarize behavior, logs describe events, and traces connect operations across a request or workflow. I would use metrics to detect a problem and traces or logs to investigate its path and cause. Common identifiers help correlation. I would deliberately choose what to collect, because more telemetry can increase cost and exposure without improving diagnosis. [S13]
What is high cardinality and why does it matter|A metric label with many distinct values can create a large number of series and increase storage or processing cost. I would avoid using per-run IDs or arbitrary user input as ordinary metric labels. Those identifiers may be better suited to controlled logs or traces. I would keep useful low-cardinality dimensions and verify the actual monitoring backend's behavior and limits.
How would you choose a trace sampling strategy|I would consider traffic, cost, important workflows, errors, and diagnostic needs. Sampling should preserve enough evidence for useful investigations and remain coherent across services. I would understand whether the system decides before or after a trace completes and what the chosen tools support. Sampling cannot be used to calculate every business total without accounting for what was omitted.
How do you instrument an asynchronous workflow|I would carry appropriate correlation context from request to job and record producer and consumer operations. The job should have a durable run identifier independent of one process. I would model retries and separate processing attempts clearly. I would avoid inventing one continuous synchronous span for work that is delayed or resumed; the tracing representation should reflect the actual workflow.
## KQL Dashboards and Alerting
How would you find a rise in errors using KQL|I would select the relevant log table, filter the time range and service, group failures into useful time bins, and compare with request volume. I would then split by version or dependency and inspect correlated traces. Table and field names depend on the telemetry schema. I would validate the query against real records instead of assuming every workspace has the same columns. [S16]
What makes a useful service dashboard|I would show user-facing health, workload volume, latency distribution, failed completions, dependency pressure, and deployment changes. Each chart should answer a clear operational question and link to investigation context. I would separate executive trends from on-call diagnostics. A dashboard full of CPU and memory charts can miss failed business operations or a broken model integration.
How would you alert on missing telemetry|I would define expected reporting behavior and compare it with received data, accounting for idle periods and ingestion delay. I would use a heartbeat or independent synthetic check where appropriate. The absence of errors is not proof of health when the service cannot report. I would test what happens if the collector or monitoring path fails, not only the application.
How do you avoid logging sensitive prompts|I would collect minimal metadata by default, such as run ID, model configuration, token counts, durations, and classified errors. Any content logging would require a deliberate purpose, access controls, redaction, and retention. I would inspect SDK and debug logging behavior. Removing content from one application log does not guarantee that intermediaries or external tools are not recording it.
## SRE and Operational Priorities
How would you choose an initial SLO|I would identify the user journey, define good and total events, choose a time window, and agree on the business target. I would check current performance and dependency constraints before promising a number. I would include correctness or completed-task behavior where appropriate for AI workflows. A target that cannot be measured consistently will not guide useful reliability decisions.
What is error budget burn rate|It describes how quickly the service is consuming its allowed unreliability relative to the budget for the chosen window. I would use it to identify sustained or fast degradation and guide response or release risk. I would define eligible events and alert windows carefully. One short error spike and a long mild degradation can require different operational actions.
How do you prioritize reliability work|I would rank issues by user impact, recurrence, exposure, and the value of the proposed improvement. I would include recovery gaps and the cost of operational toil. I would validate that the fix addresses the observed failure rather than only silence an alert. Clear owners and measurable completion criteria make the backlog useful alongside feature delivery.
What should a production runbook contain|It should identify the symptom, likely evidence sources, safe diagnostic steps, mitigation choices, required permissions, escalation path, and recovery checks. Commands need context and clear scope. I would keep it tested and linked from alerts. A runbook should help a tired engineer make a safe decision rather than prescribe a destructive action without explaining when it applies.
## Recovery Backups and Continuity
Why is replication not the same as backup|Replication can copy an erroneous update or deletion quickly, while a suitable backup preserves a recoverable prior state. I would design protection against both infrastructure failure and logical mistakes. I would check retention, isolation, permissions, and restore procedures. A healthy replica does not prove that yesterday's corrupted data can be recovered to the required point.
How do you test a backup|I would restore into an isolated environment, validate integrity and application behavior, measure restore time, and compare recovered data with the required recovery point. I would test access to keys and dependencies needed for recovery. A successful backup job is only one signal. The useful proof is that the team can restore a working service within the agreed constraints.
How would you plan regional failover|I would map compute, data, networking, identities, secrets, model availability, and routing in the recovery region. I would define activation, data reconciliation, and return procedures and test the process. I would verify capacity and quota rather than assume they are available during an incident. Regional recovery can be limited by the least-prepared dependency, even when application containers are portable.
What should happen after recovery|I would verify user-facing behavior, delayed work, data integrity, and the stability of dependencies. I would remove temporary mitigations only when safe and communicate residual risks. I would preserve a timeline and assign prevention actions. For disaster recovery, I would also plan returning to the normal topology; an untested return path can cause another outage.
## Infrastructure Cost Engineering
How do you identify idle resources|I would combine inventory, ownership, usage metrics, and cost reports. Low CPU alone does not prove a resource is unnecessary; it may provide redundancy or store critical data. I would confirm purpose with the owner and define a reversible shutdown or removal plan where appropriate. I would also check orphaned disks, test environments, and resources no longer referenced by deployments.
When would you make a capacity commitment|I would first right-size and understand the stable baseline and applicable service terms. A commitment can suit predictable eligible usage, but variable or temporary workloads may not justify it. I would compare utilization assumptions and organizational plans with the financial owner. I would avoid treating a discounted rate as savings when the committed capacity is not actually used.
How do logs affect cloud spending|Ingestion, storage, retention, and query behavior can contribute to telemetry cost. I would remove unnecessary verbose events, choose appropriate retention by purpose, and use metrics or sampling where suitable. I would preserve critical audit and incident evidence. Reducing cost by disabling all logs can make outages harder to recover from and create a larger operational cost.
How would you measure cost efficiency|I would use a unit tied to the business outcome, such as cost per successfully completed agent task, alongside total spend and quality. I would allocate shared infrastructure transparently and record assumptions. Comparing raw monthly spend can be misleading when traffic changes. Efficiency gains need to preserve the agreed service behavior and be measured over a representative workload.
## LLM Cost Controls and Fairness
What would a per tenant usage ledger record|I would record authorized tenant, run and call identifiers, model deployment, token usage where available, estimated charges, timestamps, and configuration version. I would reconcile estimates with billing and handle missing or delayed usage. Concurrency controls are needed when multiple calls consume an allowance simultaneously. Sensitive prompts should not be required to measure ordinary usage and cost.
How would you enforce a spending allowance before a model call|I would estimate and reserve a bounded allowance atomically, then settle it against reported usage after the call. I would define what happens on timeout or missing usage and retain a conservative reservation until reconciled. The estimate and billing model must match the deployment. Checking a balance without reserving capacity can let parallel calls exceed the same allowance.
When is response caching safe for AI|I would require matching authorization context, input meaning, relevant configuration, and acceptable freshness. I would include tenant and permission dimensions and avoid reuse across sensitive boundaries. Nondeterministic outputs or changing underlying documents can make caching inappropriate. I would measure hit quality and invalidation behavior rather than assume similar text always deserves the same cached answer.
How do you avoid retry driven cost growth|I would classify failures, bound attempts, honor deadlines, and account for retries at every layer. I would prevent repeated successful side effects and inspect whether partial responses or unknown outcomes should be retried. I would track attempts and cost per completed task. Retrying every failure indefinitely can increase spend while making dependency overload worse.
## RAG Ingestion and Retrieval Quality
How would you choose document chunk size|I would test representative documents and queries, considering structure, retrieval precision, context limits, and duplicated overlap. Very small chunks can lose meaning; very large chunks can dilute useful evidence and increase context cost. I would evaluate answer support and retrieval quality rather than choose a universal size. Metadata and stable references help explain where evidence came from.
What is hybrid retrieval useful for|It combines different retrieval signals, commonly lexical matching and vector similarity, to improve relevant evidence for varied queries. I would test it against the actual corpus and apply authorization filters correctly. Ranking and reranking need latency and quality evaluation. More retrieval components add operational complexity, so I would retain them only when the measured benefit justifies the cost.
How would you keep an index fresh|I would track source changes and ingestion state, process updates and deletes reliably, and record index versions or timestamps. I would monitor lag and failed documents and provide controlled reprocessing. Permission changes must propagate as well as content changes. A system that refreshes text but retains obsolete access metadata can return evidence to users who no longer have permission.
How would you investigate poor retrieval|I would examine whether the relevant source exists, was parsed correctly, is indexed, passes authorized filters, and appears in candidate results. I would compare query formulation, embedding or ranking behavior, and chunk structure. I would separate missing evidence from generation errors. Adjusting the prompt cannot fix a document that was never ingested or is incorrectly excluded.
## AI Evaluation and Quality
How would you build an evaluation dataset|I would gather representative tasks, expected evidence or outcomes, and important failure cases, with appropriate handling of sensitive data. I would include easy and difficult examples and keep a held-out set for comparison. I would version the dataset and document scoring criteria. A few handpicked successful prompts are not sufficient evidence that a change improves the production workload.
What would you measure besides answer accuracy|I would measure supported evidence, task completion, authorization behavior, harmful tool actions, latency, cost, and stability across repeated runs where relevant. I would separate retrieval and generation quality. Metrics should reflect the user workflow rather than only linguistic style. I would also inspect important failures manually because one aggregate score can hide a severe boundary violation.
What are the limitations of using an LLM as a judge|It can help scale evaluation but may have bias, inconsistency, or blind spots. I would calibrate it against human-reviewed cases, use explicit criteria, and inspect disagreements. I would avoid relying on one judge for critical authorization or safety claims. Version changes in the judge can alter scores, so evaluation configuration needs the same discipline as application configuration.
How would you detect quality drift|I would monitor a stable evaluation set and representative production outcomes, segmented by task and configuration. I would inspect changes in documents, traffic, model deployment, prompts, and tools. I would define an escalation and recovery path for unacceptable degradation. User feedback is valuable, but its absence does not prove the platform is maintaining quality.
## Agent Orchestration and State
When would you use several agents instead of one|I would use multiple agents when distinct responsibilities or controlled parallel work produce a measurable benefit. I would first compare a simpler single-agent or fixed workflow design. Multiple agents require coordination, durable state, permission boundaries, and additional debugging. I would measure task success, latency, and cost rather than assume a larger agent team is inherently more capable.
How would you checkpoint an agent run|I would persist completed steps, relevant state, configuration versions, and known external effects at deliberate boundaries. On resume, I would verify which steps are safe to repeat and whether permissions or inputs changed. The checkpoint needs enough information to recover without leaking unnecessary data. Storing only the conversation text may omit tool outcomes and irreversible business actions.
What if cancellation arrives while a tool is running|I would record cancellation durably and stop scheduling new work. I would attempt cancellation of the active call if supported, but acknowledge that the tool may already have committed an action. I would reconcile the final outcome and report an accurate state. Cancellation is not automatically rollback, so the user should know whether any effects remain.
How would you add a human approval step|I would persist a pending approval state with a clear action description, authorized approver, expiry, and audit record. Approval must bind to the exact intended action and relevant inputs; changed inputs may require new approval. The workflow should handle rejection, timeout, and duplicate responses. A message saying approved is not sufficient without verifying identity and matching the action.
## Advanced Incident Scenarios
What would you do if production DNS fails|I would determine scope and test name resolution from affected workloads, then inspect resolver configuration, private zones, records, and recent network changes. I would compare direct connectivity carefully without bypassing TLS or authorization. A temporary fix should preserve security and be reversible. I would monitor recovery and cache behavior and reconcile the corrected configuration into the normal deployment path.
What if a certificate expires during an incident|I would identify the failing endpoint and certificate chain and restore a valid certificate through the supported rotation process. I would verify propagation and client behavior and avoid disabling verification as the normal fix. I would check why renewal or alerting failed and add tested renewal monitoring. The incident can affect different layers, including ingress, outbound dependencies, or mutual TLS.
What if the database is healthy but the API times out|I would investigate connection-pool wait, network paths, application thread or event-loop saturation, transaction contention, and per-call deadlines. Healthy aggregate database metrics may hide one problematic query or tenant. I would inspect the request's trace and compare working paths. I would choose a targeted mitigation rather than assume the database needs more capacity.
What if one agent tool repeatedly performs the same action|I would pause or disable the affected path, inspect run state and attempt history, and check idempotency, timeout handling, and checkpoint recovery. I would identify actions already committed before allowing replay. A tool that succeeds remotely but times out locally can trigger duplicates. Prevention needs durable operation identity and reconciliation, not only a prompt telling the agent not to repeat itself.
## Coding and Design Follow Ups
How would you design a bounded worker pool|I would cap active work, queue size, and wait time, with defined rejection or backpressure behavior. Each task would have a deadline, cancellation handling, and observable outcome. I would ensure failures release permits and resources. I would test overload and shutdown. A semaphore limits concurrency, but a separate policy is needed to prevent unlimited waiting tasks from accumulating.
How would you test an idempotent endpoint|I would send the same key and payload repeatedly and concurrently, then verify one logical operation. I would test conflicting payloads, crash boundaries, in-progress results, expiration, and cross-tenant keys. I would inspect durable records and external side effects, not only response status. A test that calls the endpoint twice sequentially may miss the race that matters in production.
How would you design a distributed rate limiter|I would choose a rate model, identity scope, time behavior, and consistency requirement, then use an atomic shared mechanism or a deliberately bounded distributed approximation. I would define failure behavior and account for clock and network effects. I would test concurrent callers across replicas. A separate in-memory counter on each replica cannot enforce one exact global allowance.
How would you debug a memory leak|I would compare memory over time with request or job volume, distinguish heap from other allocations, and capture suitable profiles or dumps safely. I would look for retained objects, caches, buffers, listeners, or unreleased resources. I would reproduce the workload and verify that the fix stabilizes memory. Increasing limits can buy time but does not remove the retained allocation.
## Leadership and Professional Judgment
How would you hand over an unfamiliar service|I would provide an architecture and dependency map, access and ownership information, deployment and recovery procedures, dashboards, known risks, and the current backlog. I would walk through one deployment and one incident scenario with the receiving engineer. A handover is complete when they can operate the service, not merely when I have sent a long document.
How do you communicate risk to a nontechnical stakeholder|I would explain the affected user outcome, likelihood or uncertainty, practical consequence, and available options in plain language. I would state what we know and what additional evidence would change the decision. I would avoid presenting an implementation detail as the decision itself. Clear ownership and next steps help the stakeholder choose without needing to diagnose the system.
How would you mentor an engineer during an incident|I would assign a clear bounded investigation task, explain the evidence needed, and keep risky changes coordinated. I would preserve space for learning without delaying recovery or giving unreviewed broad production access. Afterward, I would review the reasoning and update the runbook together. The goal is stronger judgment and confidence, not just memorizing a sequence of commands.
What would you do if asked to promise an unrealistic deadline|I would clarify the required outcome and identify the work and constraints that drive the estimate. I would propose a smaller deliverable or phased approach and make reliability and security consequences explicit. I would communicate uncertainty early and update the estimate as evidence changes. I would commit to a credible scope rather than promise a date that depends on hidden assumptions.
